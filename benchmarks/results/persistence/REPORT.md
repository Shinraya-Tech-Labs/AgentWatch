# Persistence load

Generated by `python -m benchmarks.persistence_load` on Windows 11, Python 3.12.4, 16 logical CPUs, against SQLite on the local disk and PostgreSQL 16 in Docker. One process, one thread of Python. Writes go through the function the API uses, each in its own transaction. Every batch is a new session, so each batch also races to create one session row, which is the hardest case for that row.

| Backend | Concurrent writers | Events/s | p50 | p99 | Not stored |
|---|---:|---:|---:|---:|---:|
| SQLite | 1 | 128 | 7.3 ms | 14 ms | 0 |
| SQLite | 5 | 59 | 48 ms | 101 ms | 0 |
| SQLite | 20 | 63 | 143 ms | 376 ms | 0 |
| PostgreSQL | 1 | 110 | 8.7 ms | 14 ms | 0 |
| PostgreSQL | 5 | 167 | 21 ms | 47 ms | 0 |
| PostgreSQL | 20 | 92 | 133 ms | 264 ms | 0 |
| PostgreSQL | 50 | 117 | 219 ms | 508 ms | 0 |

Memory stayed between 127 and 134 MiB. Writes are CPU bound in the ORM: about 6 ms of CPU each. Restart with the rows stored took 12 ms on SQLite and 54 ms on PostgreSQL. The heartbeat's idle cost was 0% to 0.16% of one core over 10 seconds, at the resolution of the Windows CPU clock.

There is no earlier measurement of this workload, so these figures show no improvement or regression. They are a baseline.
